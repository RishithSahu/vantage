# 16. Native int8 engine (2026-10-27)

A hand-written C engine (`engine/vg_engine.c`) runs the whole Qwen2 forward pass with int8 maths, with assembly kernels for the Cortex-A72 (`engine/k_aarch64.h`, generated by `engine/gen_kernels.py`), AVX2 for x86 and plain C as fallback. Weights come from `models/vg_frame2r12.vgw` (475 MB, built by `tools/export_vgw.py`). It is **opt-in and off**: set `"native": "vg_frame2r12.vgw"` in `models/product.json` to use it.

## Measured on the Pi 4 (2 cores)
| Item | ONNX Runtime | Native engine |
|---|---|---|
| Prompt, 40 tokens | about 33 ms/token | 24.9 ms/token |
| Decode pass, 1 row | 135 ms | 95 ms |
| Decode pass, 8 rows | about 290 ms | 212 ms |

Prompt-time matrix maths was already at the chip's ceiling in ONNX Runtime (about 30 GOPS on 2 cores, same as my kernel): the gain comes from fusing the steps around the matrices and from one-row decode moving weights at the memory limit (4.2 GB/s).

## Batching for a server
`vg_forward` takes several sequences per call. Results are bit-identical to running each car alone (tests/test_native_engine.py). Throughput rises about 2.6x and flattens near 4 cars on the laptop (compute-bound).

## Accuracy (checked like for like, 2026-10-27)
The first Pi audit (3,443, net -14) ran without the per-vehicle hint the reference used, so it was not comparable. With the same settings (`--line all`, hint on), 3,842 questions:

| Run | Strict correct | vs reference 3,457 |
|---|---|---|
| ONNX Runtime, laptop | 3,447 | -10 |
| Native engine, laptop | 3,456 | -1 |
| Native engine, Pi | 3,455 | -2 |

The integer sums are exact; what differs are float steps (norm, rotary, softmax, SiLU), which flip borderline questions in both directions. The engine is **adopted** (`"native": "vg_frame2r12.vgw"` in `models/product.json`; falls back to ONNX Runtime if the library cannot build or load). Two tests (`test_owner_round2_ice`, "fuel level at the beginning and end of my last trip") are borderline: the model is only about 41-48 % sure and picks a different frame with the engine. The fix is training variants of that phrasing, not numerics. The other 21 failing tests (`test_records`, `test_vehicle_platform`, `test_model_route_formats`) also fail with ONNX Runtime alone.

Note: `models/product.json` lost `"vehicle_hint": true` when it was recreated on 2026-10-24. Restoring it makes `test_corpus` fail (electric car asked about fuel), so it was left off.

## Whole assistant on the Pi (100 questions, 2 cores, text in to answer out)
| Run | Median | p95 | Over 2 s | Peak memory |
|---|---|---|---|---|
| ONNX Runtime | 1.24 s | 2.66 s | 12 | 1.40 GB |
| Native engine | 1.11 s | 2.59 s | 10 | 1.34 GB |
| Native + query fixes | 1.11 s | 2.41 s | 8 | 1.09 GB |

Where the rest goes: prompt tokens. A 30-45 token question costs 0.8-1.4 s of prefill at about 25 ms/token, which is the Cortex-A72 int8 ceiling on 2 cores (no dot-product instruction). Under 2 s for every question is not reachable on this CPU by arithmetic alone; it needs fewer prompt tokens or more cores or a chip with dot-product (Pi 5).

## Why so many questions were slow on the Pi (full pass, 2026-10-27)
A full pass of all 4,096 questions on the Pi (2 cores, native engine, 4-year electric car) found two different causes, and one cascade that made it look worse than it was.
- **A stuck worker.** One question's full-history scan ran 60 s. The assistant has one worker, so every question after it was answered "busy" (1,270 of them, in under 0.05 s each; they were never really answered). `ui/server.py` now interrupts the running database statement when a question passes its deadline, so the worker is free for the next question (tested: the next question answers in 0.1 s).
- **Whole-history scans through Python.** Four years of minutes is 2.1 million rows; SQLite hands them to Python at 3.5 microseconds a row on the Pi (7 s). The health summary ("is my car ok"), the daily means, the first day the coolant flow dropped, the latest abnormal reading, nearest-sample lookups and the long-window frame loader each did this one or several times per question (3 to 12 s on the Pi).
- **Model-bound.** Prompts with a 40-70 token tail (the glossary hint line of 2-4 terms) cost 1 to 2.4 s of prefill at 25 ms a token. About 8 % of the questions are over their limit by the model alone; this is the CPU, not the database (see below).

## The column copy and what uses it (all exact, all live-safe)
`vgpt/colstore.py`: a copy of each per-minute table as one binary file per column (float64, NaN for NULL) in `<database>.cols/`. A window is two binary searches and a slice of a memory-mapped file; nothing is copied. It is an index of stored data, never of answers.
- **Live data.** Rows that arrive after the copy was made (the live writer adds a row a minute) are read from the database on every call and added at the end; after 1,000 of them the copy is extended in the background (append only, description file replaced last); more than 200,000 and it is rebuilt. Before each use the copy is checked against the database (first time, last row's value, 14 spread-out rows); a copy that fails is ignored and rebuilt. Windows shorter than 3 days, and tables not yet copied, read the database as before.
- **Start-up.** `colstore.warm_async` (called when the app adopts a database) starts the copy of the signal table if there is none and otherwise reads the files into the operating system's file cache; the first question after a boot used to wait 2 s for the SD card. It holds no answers and predicts no question.
- **Users of the copy** (`vgpt/fastcols.py`, each returns exactly what its SQL returned or None, and then the SQL runs): `qa_b.daily` (daily means), `qa_core.flow_days`, `baseline_stats`, `last_abnormal`, `qa_core.load` (per-minute branch), `contracts._signal_days`, `pairs.minute_series`, `digest._energy_level_line`, `query_executor._daily` day counts, the frame loader (`_load_frame`), the tyre batching (`qa_core.attach_tyre`). `vgpt/nearest.py` replaces seven `ORDER BY ABS(ts - ?) LIMIT 1` full scans by two index probes (same row, same tie choice). The latest-tyre-reading lookup tries the last 2 days first (the grouped view was built over the whole history, 0.8 s).
- **Laptop timings** (4-year database): daily flow means 0.229 s -> 0.009 s, `last_abnormal` 0.183 -> 0.017, `flow_onset` 0.194 -> 0.010. **Pi** (warm): 0.04, 0.06, 0.05 s; the first call after a boot is 1.7 to 1.9 s without the start-up warm-up.
- **Tests.** `tests/test_fastcols.py` (every function against its SQL, on a generated history with NULLs and a non-UTC day, with rows appended in three steps, with a writer thread appending while the answers are compared inside one snapshot, and on the real 4-year database), `tests/test_nearest.py` (ties, NULLs, before the first and after the last row, real database), `tests/test_colstore.py`, `tests/test_frame_loader_equivalence.py`, `tests/test_daily_equivalence.py`. `VGPT_FASTCOLS=0` turns the new users off, `VGPT_COLSTORE=0` the copy.

## The history is not append-only (found on the Pi, 2026-10-28)
The first Pi passes with the column copy showed single questions stalling 20 to 60 s. Causes, all fixed in `vgpt/colstore.py`:
- **The live store rewrites and drops rows.** The rollup replaces a minute row when the minute finishes (`INSERT OR REPLACE`), and the retention (`store.compact`) deletes the oldest rows. The first validity check (value of the last row, first row unchanged) failed on both and rebuilt the whole copy (27 s) about every 90 questions. Now the last `GUARD` = 30 rows are re-read from the database and overwritten in place at every call, the validity check uses a row older than the guard, and rows the database no longer has are clipped from the window. Test: `test_colstore.py::test_rewritten_newest_rows_and_dropped_oldest_rows_do_not_force_a_rebuild`.
- **A question waited for an unrelated build** (one write lock per store, held by a long build of a lake view). Now one lock per table, and the in-question append never waits (busy: it reads the few new rows from the database instead).
- **First use of a table scanned it through Python** (20 to 60 s) while the copy built in the background. Now the copy is made in one pass on the spot (about 8 s for the signal table on the Pi) and used by that question; the signal, extension and camera tables are built at start-up. A grouped view (the tyre view) is never copied (seconds to materialise).
- **Any error is a fallback.** Every fast path is wrapped (`fastcols._safe`) and the copy's reader returns None on any exception, with a 60 s to 5 min back-off, so a problem in the copy cannot reach a question.

## Hints without training (2026-10-28)
Glossary hints are 5.5 prompt tokens per question on average and 21 on the questions with 40+ token tails. Two data-only changes, both switched on by `"hint_short": true` in `models/product.json` (`VGPT_HINT_SHORT=1`):
1. **Compact meanings** (`vgpt/meaning/glossary_short.json`): hand-written shorter meanings for 42 terms. Four terms (12 V, top speed, kWh, check engine light) and "efficiency" lost accuracy or a product test when shortened and keep their full text. Combustion cars keep their own full meanings.
2. **Hints the model does not need** (`vgpt/meaning/glossary_skip.json`, found with `bench/hint_ablation.py`: every term removed one at a time from the 3,842 audit questions): pack, regen, rpm, dtc, hvac, top speed, fortnight, adas, seats, plug in, disengagement, capacity lost nothing and get no hint for non-combustion cars (the other terms lost 1 to 5 questions when removed and stay).
Result: hint tokens over the 4,096 questions 22,375 -> 13,541 (-39 %). Audit of the combination (3,842 questions, same settings as the 3,457 reference): **3,457**, product tests unchanged (the two known trip-bounds failures). Rejected on the way: all compact meanings together (3,454, and one product test failed), first-clause hints (one product test failed).

## Still open
- 211 questions are over their limit by the model alone (prompt tail 40+ tokens at about 35 ms a token including attention, 3 or more decode passes at 156 ms). Without training the remaining levers are fewer decode passes, a shorter question template or a faster CPU (Pi 5, dot-product).
- The 1.8 M-row cap in `_load_frame` drops the newest 14 % of a 4-year history, and "compare cold and hot days" still loads four years of minute data in Python; both change answers if fixed, so they need the owner's decision.
- `digest._parked_stretches` and `trips_between` are Python loops of 20 to 50 ms on the Pi.
- Nothing of this is deployed to the Vantage service on the Pi (it still runs the old ORT code); the test copy is `~/vg_e2e`.
