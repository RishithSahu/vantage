# VANTAGE - current status report (7 Oct 2026)

This is the one current report. Older reports and working logs are archived in `docs/history/` and must not be quoted. **Every accuracy, latency and test figure below comes from one source revision, hash `d12507ef45486c64`** (136 Python files; `results/final_manifest.json` also records the model, database and question-file hashes and the runtime versions; `results/final_manifest_current.json` shows the same hash at the time of writing). Figures are configuration-specific: each table names the configuration it describes.

> **Update (section 13):** a retrieval + frozen-SLM understanding layer was built and measured. The recommended configuration is now the **hybrid** (rules answer what they fully support, the model handles the rest): dev 80 / final 142 correct versus 73 / 132 for the rules product. The pure model route is far weaker (41 / 73), and every question that reaches the model takes about 4 s on two laptop cores.

## 1. What VANTAGE is, and the honest summary

An on-device vehicle assistant. **The product configuration** (`vgpt.product.make_brain`, used by the UI and `app.py`) is: a deterministic rule parser and typed query IR, an interpretation contract (provenance + support + coverage checks), a deterministic candidate generator, a clarification-first policy, a whitelisted read-only SQL planner and executor, evidence contracts and an answer verifier. **It contains no language model on its answer path.** Two model configurations were measured as experimental comparators (a frozen LFM2.5-350M candidate selector; the earlier Qwen2.5-0.5B + LoRA whole-query model). Also present: schema overlays for other vehicles, and ingestion decoders for CAN/SOME-IP/VHAL/logs/NMEA (replayed, not live).

What the measurements support:
* **The listed engine operations passed the specified independent checks** (windows, aggregates, counts, rankings, retention, paging and the explanation arithmetic against plain SQL/numpy; schema changes end to end). That is not a claim that every possible query is correct.
* **Language understanding is the weak part and generalises poorly.** The rules alone answer 77 of 120 development questions correctly and 137 of 308 (44%) on the older final set (regression data), where 38 of their 143 answers to answerable questions (27%) are wrong. Development figures are optimistic: the rules were improved while reading development failures.
* **The clarification-first policy is a risk/coverage choice and it lowers coverage.** Against the rules alone, the product configuration gives fewer directly correct answers (73 vs 77 dev; 132 vs 137 final) and fewer answers (66 vs 69; 128 vs 143 to answerable questions) with fewer wrong ones (6 vs 8; 27 vs 38). The share of answers that are wrong falls from 11.6% to 9.1% (dev) and 26.6% to 21.1% (final); that is a trade of coverage for fewer errors, not an accuracy gain on the same questions. See section 4.
* **Clarifications often do not contain what the person meant.** On the final set 86 of 135 clarifications offer no intended reading (84 on answerable questions, 2 on questions that needed none); on dev 17 of 39. This is the largest failure category. "Correct after one extra turn" in the tables is an **oracle upper bound** (a person who always recognises and picks the right reading); real user success was not measured.
* **The small model's contribution is not demonstrated.** The frozen LFM selector fails the pre-registered criteria against the stronger baseline; the Qwen-LoRA gives more directly correct answers but also more wrong ones, ignores conversation history through its interface, is fine-tuned, and has a model path above 2 s at p95 on the laptop. The no-model configuration is a **control**, not the completed VehicleGPT: the case study asks for an SLM/LLM and this repository does not show one that earns its place.
* **No ARM measurement exists.** All timings are x86 laptop cores (2 pinned). QEMU is deferred at the owner's request.
* The sealed **acceptance set is an unreviewed draft** and has never been run on any system.

## 2. Constraints kept
No new training; no model downloads; no AWS spend; QEMU stopped; retrieved examples and `--complete` off by default; the acceptance file was not used for any development decision; no question-specific branches or benchmark-ID handling. Changes made in this revision are generic (a verb gate, a status gate, an interval rule); none was written to fix an individual evaluation question, although defects were found by running the evaluation questions through the product route and the fixes were then verified on them, so the development and final sets are regression data.

## 3. The product route (what the UI actually runs)
**Audit** (`bench/route_audit.py` -> `results/route_audit.md`; `bench/five_questions.py` -> `results/five_questions.md`): the five PDF questions verbatim and representative failures, on two generated vehicle histories, through `make_brain`. For each: route, interpreted query, evidence class, verifier status, displayed answer. **All 10 PDF-question runs leave through the typed pipeline** (route `qc`).

**End-to-end evaluation** (`bench/eval_product.py`, scored with the same evaluator as the baseline): every development / diagnostic / final question is asked through `make_brain`, so the gates, the policy, the typed pipeline and the routing to older engines are all in the path. It agrees with the interpretation-only harness (`policyrules` rows) on 120 of 120 development questions, 30 of 30 diagnostic and 307 of 308 final questions (the difference is "thanks", answered by the small-talk route; `results/product_vs_harness.txt`). A refusal-gold question that an older engine answered with analysis would be counted as a false action: there are none (dev 0 of 12, final 0 of 21).

**Routes.** Typed pipeline (`qc`): every statistic, event, comparison, explanation or history question. Older engines (`qa`, `fast`, `rules`, `gate`): greetings, help, units, glossary, safety refusals, and **present-state status / health summaries** ("how's my battery", "is the camera blocked right now") that the policy defers by an explicit rule. **These older routes are not claimed to carry the typed checks** (no evidence contract, no answer verifier). Since the review: when the policy declines to form an executable reading, an older engine may no longer answer a statistic/event/comparison/status-guess question (previously "what does a ford focus cost" and "open the windows please" received unrelated analytical answers from older routes); the person gets the policy's own question or limitation. In the dev set 8 of 120 questions, and in the final set 19 of 308 (mostly refusals and out-of-scope requests; 3 are present-state questions answered by the status engine), leave the typed pipeline.

**Defects found by the audit and fixed (each has a test in `tests/test_product.py`):**
* *Fuel efficiency on an electric vehicle:* the PDF question is no longer silently answered as "energy efficiency". The assistant states that the vehicle is electric and records no fuel data, offers the electric equivalent (average energy consumption, Wh/km) as a reading, and accepts "yes", "1", or "neither of these" (the latter clears the offer without answering). The "I answered for energy used" note, which contradicted the Wh/km answer, is gone ("energy efficiency" is one concept, not two signals).
* *Range explanation:* the displayed basis now reads "range = usable capacity / (total energy / total distance of each period)"; the claim that the remainder "is not explained by anything the car measures" was replaced by "not accounted for by the recorded conditions in this model (it may come from something that is not recorded, or from what the model cannot capture)".
* *"Before the warning":* the window is stated ("the 10 minutes before the battery over-temperature warning on 21 Sep, 14:53 (the interval 14:43 to 14:53; the event itself is the anchor and is not part of these figures)"), and the executor now **excludes** the event's own sample (it previously included it; a unit test fails on the old behaviour).
* *Control requests* in any word order ("switch off the lane assist", "open the windows please", "turn the air conditioning off") are refused by a gate and never reach an analytic route (previously some were answered with unrelated analysis). The same gate applies to the experimental selector path, which lacked it.
* *Past-tense existence questions about events* ("was the camera blocked today") are counted instead of asking whether the person wants the latest event or the number; *the Hinglish detector* no longer fires on an English "me me".
* Clarification menus end with "neither of these" in every case; the generator's readings are never answered without confirmation.
* Known remaining defect: "has the camera been blocked in the last 7 days" is parsed as an average blockage statistic (an existence question about a signal, not an event); it is answered, and wrongly.

**Coverage dropped, as the stricter policy implies, and it was measured, not assumed.** The previous revision of this policy auto-answered a generator reading when it passed the structural checks; it answered more (84 dev) and was wrong more (12). **Candidate availability** (a property of the generator, apart from selection, apart from user success): the intended query is among the generator's candidates for 83 of 108 answerable dev questions (76.9%) and 167 of 287 final questions (58.2%); mean 4.9 / 4.4 candidates (`tools_cand_availability.py`, `results/cand_availability_*.json`). The product offers at most three readings, so the clarification hit rate (above) is lower.

## 5. Bounded model-role experiment (pre-registered; one run per configuration)
Variant: the deterministic generator proposes readings; the frozen LFM2.5-350M only chooses an index; a chosen reading is answered if it passes support + coverage, otherwise offered.
* **First run (earlier revision, baseline = rules + policy without the generator):** all pre-registered criteria met.
* **Final revision, same criteria, baseline = the product configuration:** latency criterion met (model-path p95 1.2 s); wrong answers **11 vs 6 (fails)**; correct + clarifications containing the intended reading **91 vs 95 (fails)** on dev; on the final set 171 vs 181 and wrong answers 53 vs 27. The selector answers more directly (78 vs 73 correct on dev) at the cost of more wrong answers. The criteria were fixed before the run and are not changed.
* **Transfer criterion** (new signal described only by label and synonyms, 10 questions): the intended reading was available for 9 of 10 and answered directly for 8 of 10, all 8 by the rules (the overlay rebuilds the vocabulary); the model-attributable part is at most one offered clarification (`results/transfer_select.json`).
* **Verdict: the frozen small model has no demonstrated role.** The selector stays disabled (`selector=None` in the product configuration) and is not tuned further. The only change made to its path was the read-only gate (a safety rule shared by all configurations).
* **Qwen-LoRA:** retained as an experimental comparator and optional fallback. Its interface takes the question only (no conversation history), it needed fine-tuning (no new training was done), and its model path exceeds 2 s at p95 on the laptop (dev p95 2.4 s, final p95 2.5 s). A model trained to choose among candidates, or to fill only unresolved fields, is the untested next step.

## 7. Interpretation, clarification, schema transfer, executor
* **Interpretation contract** (`vgpt/interpretation.py`): provenance for operation, targets, statistic, periods, thresholds, groups, selection, event and units; support and coverage checks; disclosures state the actual period.
* **Clarification-first policy** (`vgpt/policy.py`, `candidates.py`, `paraphrase.py`): answer / clarify with concrete readings and a "neither of these" choice / refuse. Gates in order: control requests (refused, never clarified), fuel on an EV, present-state status questions (older status engines). A clarification is never resolved by guessing: "neither", or a number past the last reading, clears the offer and asks the person to say it in other words.
* **Schema transfer and missing capability** (`bench/schema_fixtures.py`, `tests/test_schema_transfer.py`, 10 end-to-end tests): missing front-left pressure (never replaced by another wheel), aggregate-only pressure, different stored units and scales (offset supported), registered-but-empty signal, intermittent signal (coverage stated), motor vs steering torque, a brand-new signal supporting all generic operations, an opaque identifier. **Not covered:** a vehicle whose buses (not storage) differ; renaming identifiers of signals the older engines hard-code.
* **Executor / retention:** the interval is enforced exactly before aggregation (partial days, boundary samples) and **a midnight-crossing trip is now tested** with a constructed fixture (a trip inserted into a copy of the history that starts 20 minutes before local midnight: counted on the start day only, +25 km, the next day unchanged, equal to plain SQL; `tests/test_windows.py::MidnightCrossing`). Coverage is judged against days with recorded trips or charges; event lists are retrievable in full by paging. These were verified on generated 28- and 90-day histories only.
* **Explanations:** distance-weighted decomposition so the explained quantity equals the headline. Against counterfactual twins (13 roof-box pairs): the unrecorded cause stays in the unexplained part by a median 0.70 (min 0.30); in 6 two-cause families a recorded gradual factor can absorb 2-6 Wh/km of credit although its true effect is about 0 (it moves with the period) - the answer now says when a factor moved together with the period. Change points are exploratory (serial correlation). **Associated, not causal.**

## 11. Open items and limitations
1. **ARM hardware or QEMU latency and memory: not measured** (deferred by the owner). `python vm/driver.py smoke` runs the guest benchmark; results must be labelled emulation.
2. **Acceptance set unreviewed and never run.** The freeze is deferred until the configuration is chosen: review the gold interpretations without looking at predictions, then freeze with an explicit `--system` (`docs/acceptance_review/README.md`; neither `bench/freeze_acceptance.py` nor `bench/run_acceptance.py` has been executed).
3. Rules and conversation sets were tuned on failures and are regression data; the old 308-question set influenced the vocabulary. One author wrote the vocabulary and every question set.
4. The policy trades coverage for fewer errors (section 4); choosing the operating point is an engineering decision the case study does not supply. It may cost usability: 135 clarifications on the final set, 86 of them without the intended reading. No user study exists.
5. **The SLM requirement is not met by evidence** (section 5).
6. **Older engines remain on the product route** for non-typed intents and present-state status/health summaries, without evidence contracts or verifiers. A few present-state phrasings may therefore be answered by an older engine while an equivalent historical phrasing goes through the typed pipeline. Domain engines for tyres, weather, service and driving are reachable only when the typed policy produces no reading; otherwise the typed pipeline clarifies (it may offer a generic reading such as total distance for a service question, with "neither of these").
7. Questions the rules and generator cannot read are refused with a request to rephrase (e.g. "compare the last two weeks with the two weeks before that", "hardbraking count last month"), where an older engine previously answered some of them correctly; this is the preferred trade (clarification or an explained limitation over a speculative answer).
8. Event lists, paging and retention were verified on generated histories only; protocol decoders run on replayed traffic; no real vehicle, CARLA or Raspberry Pi run exists.
9. Opaque identifiers are supported for signals registered by overlay; renaming identifiers of signals the older engines hard-code is not.
10. Isolation: only the software boundary is tested (read-only store, whitelisted SQL, no transmit path, control-request gate, neutralised log text). Vehicle-level isolation (hypervisor/SoC separation, a hardware one-way gateway, ASIL partitioning) is a proposal (`DESIGN.md` section 1).

## 13. New direction: retrieval + a frozen SLM write the plan (built 7 Oct 2026; section 13 supersedes sections 1-5 wherever it says otherwise)
**What was built (no training, no fine-tuning, no AWS, no QEMU).** The rule-driven understanding layer was kept as a baseline and a second one was added next to it (`vgpt/assistant.py::SlmBrain`, selectable as `make_brain(route="slm" | "hybrid")` or the `VGPT_ROUTE` environment variable; the default is still `rules`, see the verdict below):
* **Capability registry** (`vgpt/capreg.py`): signals, events, named conditions, trip classes, ranking metrics and six domain tools (service, tyres, weather, driving, health, places) described from the schema; availability from the data profile; related capabilities (a camera-blockage signal and its event stream); overlay-defined signals (opaque identifiers, new signals) included automatically.
* **Hybrid retrieval** (`vgpt/retrieval.py`): SQLite FTS5 (BM25) + BAAI/bge-small-en-v1.5 (ONNX int8, 34 MB) fused by reciprocal rank; floors, not forced top matches ("tell me a joke" retrieves nothing). The intended capability is among the retrieved top 3 for 97% (dev) and 93% (final) of the questions that name one.
* **Frozen LFM2.5-1.2B-Instruct (Q4_K_M, 731 MB)** writes the plan in two focused calls (`vgpt/understand.py`): stage A chooses one of 21 typed functions (an embedding shortlist from an example bank, then the model); stage B fills that function's arguments in the model's native tool-call format, from a prompt that holds only that function's examples, under a grammar generated per question from the capability registry (the identifiers it admits are the retrieved ones). Each stage's prompt is a cached model state (a hybrid-recurrent model can reuse a prefix no other way).
* **Gates on invention channels** (deterministic validators, not parsers): a period only if the question contains temporal vocabulary (typo-tolerant), a threshold only if it contains a digit, a unit only if it names one, a condition only if retrieval offers it after a restriction-introducing word, a removal only if the question says so. Otherwise the argument is absent and the documented default is applied and disclosed.
* **Deterministic state update** (`vgpt/compiler.py::merge`): a follow-up states only what changes; "actually city only" replaces the driving mode and keeps period and signal; "without the rain restriction" removes one condition; a threshold on a signal replaces the old one. State comes from the system's own previous turn (never from gold history).
* **Typed semantics** added for the known defect classes: existence ("was the camera blocked": yes / no / **cannot say no** when the period is not fully observed; a signal with a related event stream uses the event records), totals for accumulating quantities, free-text clarification replies, "neither of these" always available, model replies limited to closed lists (the model never writes reply text or numbers), a plan that is truncated or malformed is never executed, and a plan the interpretation contract finds unsupported is **shown back for confirmation instead of executed**.
* Every executable route is a typed query through the existing validator -> planner -> executor -> evidence contract -> verifier, or a domain tool with an explicit evidence statement; there is no fall-through to the older routes.

**Measured (same questions, same evaluator; follow-ups use the system's own state; clarification "hit" = an offered reading contains the intended meaning):**

| route | dev correct | dev answers / wrong | dev clarify / hit | final correct | final answers / wrong | final clarify / hit |
|---|---|---|---|---|---|---|
| rules product (section 4) | 73 | 66 / 6 | 39 / 22 | 132 | 128 / 27 | 135 / 49 |
| **model route** (retrieval + frozen LFM2.5-1.2B, confirms unsupported plans) | **41** | 39 / 8 | 71 / 4 | **73** | 66 / 15 | 213 / 18 |
| **hybrid** (rules answer what they fully support, the model handles the rest) | **80** | 78 / 9 | 30 / 12 | **142** | 144 / 30 | 127 / 44 |

* **The model route alone does not understand well enough.** Without the confirmation step it answers more (dev 44 correct, 54 wrong). The interpretation contract removes most wrong answers (a flagged plan was correct about 1 time in 23, an unflagged one 8 in 11), but the clarifications it then asks almost never contain the intended reading (4 of 71 on dev). Stage attribution on dev: with the **correct function given**, the same stage B reaches 65 of 120, so about 21 questions are lost to function selection (the model chooses the right function for 69% of non-follow-up dev questions, the embedding shortlist alone for 59%, and on the final set 54-60% for either). Stage B itself is the other bottleneck (wrong signal among the candidates, wrong period).
* **The hybrid is the best configuration measured**: +7 (dev) and +10 (final) directly correct answers over the rules product and fewer clarifications, at +3 wrong answers on each set. The improvement is real but small. It is **not** a demonstration that a small frozen model generalises to unfamiliar language: the final set (unfamiliar wording) is still only 142 of 308 (46%).
* Failure categories in the model's plans: operation confusions (explain a change vs ask when it changed vs trend; "what happened before the warning" read as "why did the warning happen"), wrong signal among the candidates, invented or mis-mapped periods, a leading bias to `extreme` / `ask_user`. None was fixed by adding phrase rules. The worked examples (`vgpt/intent_bank*.py`, `vgpt/arg_examples.py`) are the only natural-language knowledge, written independently of the evaluation sets and checked by a test (`tests/test_understand.py`) not to come within 0.93 embedding similarity of any development, final, diagnostic or conversation question (the acceptance file was not read).
* **Latency and memory (inside the simulated target: Windows Job Object, 2048 MB committed limit shared with a 700 MB OS ballast and the ingest daemon, 2 pinned cores, no QEMU; laptop cores, NOT Cortex-A5x; `results/perf_slm.json`):** the whole job peaks at **1,792 MB of 2,048 MB** (assistant working set 1.6 GB with memory-mapped weights). The first attempt did not fit, because 22 prefix states of 25-130 MB each were held in RAM; now two stay resident and the rest load from disk. Model-route latency per question: mean 4.1 s, p95 4.9 s, max 5.3 s (retrieval 19 ms, stage A 1.2 s, stage B 2.8 s, compile and execute milliseconds); **all 40 measured questions exceed 2 s**. Prefill runs at about 35 tokens/s and decoding at about 16 tokens/s for this model on two laptop cores, so the 2 s requirement is not met for any question that reaches the model; on a slower ARM core it would be slower, which is **not measured**. The hybrid answers the questions the rules support in milliseconds and sends the rest to the model (mean 2.2 s per question over the final set, p95 5.2 s). Cold start: model + embedder + stage-A state about 4 s from disk; building the 22 prompt prefixes once costs about 10 minutes and about 1 GB of disk, then they are cached. Ingestion keeps up (502 msg/s, lag 1.0 s).
* **Adaptation without parser changes** (`bench/adaptation_demo.py`; `results/adaptation_demo_slm.md`, `results/adaptation_demo_hybrid.md`): same model, same prompts, only overlay and data change. Retrieval finds an opaque identifier (CH_0417) from its description, a signal the registry never knew (washer fluid), the units fixture, the missing-front-left-tyre fixture (an explained limitation, nothing substituted) and the partial-history fixture (the answer states the days covered). On the model route about half of the plans are wrong (for example "lowest tyre pressure" planned as an event explanation), which is the same limitation as above.
* **The PDF's fuel question** (`bench/fuel_vehicle.py`): on the EV the fuel signals are known but not recorded and the assistant says so (`fuel_level (not recorded)` is retrieved; it offers the electric reading and a neither path). On a clearly labelled **simulated fuel-capable vehicle** (the EV history plus simulated fuel rate, level and efficiency, with a 15% efficiency loss over the last 14 days) the same generic change detector answers "When did fuel efficiency show the largest drop?" (level before 10.0 km/L, after 8.8 km/L); no handler exists for that question. The pure model route plans it as `explain_change` (a wrong function) and asks; the hybrid answers it through the rules after the overlay rebuilds the vocabulary. The simulation is not data from a vehicle.
* **Verdict.** Not the pure model route: it is far below the rule-based product on accuracy and about 100x slower. The recommended configuration is the **hybrid**, and the case-study requirement "a local SLM that understands user questions" is only **partly** met: the model contributes on a minority of questions and its measured contribution is modest. Granite 4.0-1B (the planned second comparison) was not downloaded (not approved), so the bounded two-model comparison was not run; the schema-conditioned encoder alternative (GLiNER2) was not tried. No further tuning rounds were spent.
